    Research: Keeping a spec faithful to its record (BK-503)¶

    Date: 2026-10-29 Backlog items: BK-503 (A record's spec, model and reference model have no faithfulness gate, so a misreading of the record reaches every layer built from it) Status: Research complete. Background to RFC-0029; it decides nothing.

    No published pipeline takes prose decision records to a spec, models and an executable reference model with gates that check faithfulness to the prose, so the best-supported design is assembled from analogues, and its central claim is unmeasured. That claim is that oracles derived from the records catch spec misreadings that every spec-derived check misses. The design writes the record-derived check set before the spec so that the set stays blind to it; RFC-0029 R4 keeps that blindness with a read scope instead, so a spec may exist while the set is written.

    1. Question and method¶

    The question, from the brief: once an /observe record is complete, how can the spec, formal models and reference model built from it be shown, as early as possible, to be faithful to the record, free of conflicts, satisfiable, and bound by two test families, one derived from the spec and one from the record. Agents do most of that work.

    The full results, with grades and a citation per claim, are five reports in the haalfi/research repository at fc762e6, branch research/spec-faithfulness-and-enforcement. Their own precedence, stated in the summary report, is: deep dive over verified edition over the original, which is superseded; the trial design is a separate protocol. A follow-up on the same branch at 193c0bc verified nine leads another tool named and changed no recommendation (§ 2.2). A second, the current-evidence check at c1f2cd0, verified six more and changed none either; the summary at that commit consolidates all six reports.

    2. Results¶

    2.1 What the evidence carries¶

    2.2 Gates and pipelines¶

    The deep dive's gate sequence, G0 to G9 (summary § 2), each blocking the next stage for the clause it covers: G0 ID and schema lint; G1 upward trace; G2 faithfulness exhibition against the record; G3 tables complete and disjoint; G4 conjunction, split into G4a per-operation response existence, G4b invariant preservation, G4c bounded confirmation and G4d full checks run nightly; G5 vacuity, before any G4 or G4a pass is trusted; G6 model to reference-model conformance; G7 downward trace and coverage, a presence check only; G8 per-family mutant kill at equal test counts; G9 spec-strength mutation.

    Of the candidate pipelines (summary § 3), Pipeline A is the one the evidence calls feasible in pure Python today (summary § 3): G0; a record-derived check set written in a fresh, records-only session under a file-system read scope, before the spec; the spec; G1 and G2; G3, G4 with G4a and G4b, and G5; the reference model, driven by a Hypothesis state machine; G6 to G8. It runs neither G4c nor G4d. Three alternatives are kept, whose precedents are all outside API specs: Pipeline B translates every clause into one common logic over one shared signature and checks them together; Pipeline C writes one executable formal source and generates the other layers from it, literally Dafny compiled to a Python reference model; Pipeline C′ writes Quint as the executable source and replays its simulated traces against a separately written Python model.

    The prior-art check (193c0bc, § 3 and § 4) names the nearest published pipeline: Lim et al. (FM 2026) run prose to formal assertions to a model, with a human review of each assertion against its requirement, and stop at the formal model; ARSENAL runs end to end with no check against the prose. The one measured automated check of a formal artifact against its prose source (claimcheck) reports recall only against mutation-built labels, with no precision against human labels. It adds one unmeasured idea: freeze formal assertions once reviewed, so an agent repairing a model cannot weaken them.

    2.3 What is unmeasured¶

    • The central claim. The trial design (§ 1) measures it on one operation: 60 misreadings seeded upstream, every spec-derived layer regenerated from the misread artifact, and the share caught by record-derived oracles and missed by every spec-only check (S⁺, defined in § 2.4) estimated with an interval. At n = 60 it can confirm a large effect or refute the claim for that operation; it cannot rank pipelines or speak to other operations.
    • How many wheats suffice, for any stateful API (deep dive § 4).
    • How often alpha, the mapping from the reference model's state to the spec's, is itself wrong in a test-based bridge (deep dive § 4).
    • The trial's cost. The protocol's estimate rests on assumptions it labels unsourced; a dry run on a toy operation is what replaces them.

    2.4 The trial's terms¶

    These are the trial design's definitions (§ 1 to § 3), restated so that RFC-0029 can be read without the external reports. Section numbers below are the trial design's.

    • Reference model (R). An executable model of the operation, here in Python, against which every test runs. alpha maps its state to the spec's.
    • E and S⁺. E is every oracle written from the record alone, by a session that sees neither the spec nor anything built from it (the record-derived check set and the expectation tests). S⁺ is every check that never consults the record: gates G0, G3 (over the spec's tables), G4 with G4a and G4b, G5, G6 and G9, and the spec-enforcing tests (§ 2.0). G1, G2, G7 and G8 consult the record or both families, and Pipeline A runs neither G4c nor G4d (§ 2.2), so none of these is part of it.

    • Seeded misreading. A deliberate wrong reading of one record clause, planted in the spec, after which every spec-derived layer is regenerated from the misread spec (§ 2.2). Six classes, ten seeds each:

      Class Misreading
      C1 Lost case: a table row or scenario branch dropped
      C2 Added commitment: a value or order fixed that the record leaves open
      C3 Reinterpreted option: the record's rejected option adopted
      C4 Wrong non-commitment type, for example unspecified retagged as deliberately not promised
      C5 Wrong environment exposure: an environment action or fault exposed or hidden
      C6 Cross-table contradiction: one cell changed so two tables disagree

    • p10, p01, delta. p10 is the share of seeds E catches and S⁺ misses; p01 the reverse; delta = p10 − p01.

    • Wheat and chaff. A wheat is a correct reference model that makes different choices wherever the record leaves behaviour open; checks are screened against two before they gate, and 24 held-out wheats measure what over-strictness remains. A chaff is a deliberately wrong model encoding one conceptual misreading, such as a rejected option; a useful check set rejects it.
    • Validity condition V. E rejects at most 1 of the 24 held-out wheats (the upper bound of the 95 % Clopper–Pearson interval at most 0.25), majority over five runs. Without it, a suite that fails on everything would "catch" every seed (§ 2.0, § 3.1).
    • Hypotheses (§ 3.1), tested in a fixed sequence:
      • H1 (primary): E catches misreadings that every check in S⁺ misses. Supported if the lower bound of p10's 95 % interval is at least 0.05 (at least 8 of 60) and V holds.
      • H2: E catches more than S⁺ overall (delta > 0).
      • H3: at equal test counts, expectation tests catch misreadings that spec-enforcing tests miss.
    • Tiers (§ 2.8). The core tier runs Pipeline A only, enough for H1 to H3; the full tier adds Pipelines B and C′ for a descriptive comparison.
    • Lineages and roles (§ 2.3). A lineage is a model provider. Four distinct ones fill four roles: X writes the spec and regenerates the spec side per seed; Y writes E from the records alone; Z, used by neither family, seeds the misreadings; W judges as a spec-blind reviewer. Raters are people: P1 the maintainer, P2 an external second rater, optional P3 an adjudicator.
    • Criteria for the operation, O1 to O11 (§ 2.1). The trial operation has: a complete and disjoint case table of at least four rows (O1); a state × operation table over a handed-out object, at least three states (O2); at least two environment actions, one a fault or cancellation and one a concurrent or out-of-band actor (O3); an interval operation under a history predicate (O4); at least three of the five non-commitment types, unspecified and deliberately not promised among them (O5); at least two profile values with a declared deviation (O6); at least 60 distinct seed loci (O7); a complete record frozen at a revision (O8); at least one documented past real misreading (O9); no use in earlier trials or public reports (O10); a feasible Python reference model with a Hypothesis state machine (O11).

    3. How it meets this repository¶

    The research was briefed without the repository, so four of its premises need correcting before they bind anything here.

    1. The observed failure modes sit in the record, one step before every gate. OP-01's record carried decision text no dialog asked (OP-01/O14 to O16, O31), tables and lists in one decision that another contradicts (O27, D34's E7 row against D12; O33, D34's changed row against D26; O39, D35's list), and a consistency check that passed and was wrong (O29, D41's "no row contradicts a decision"). The trial seeds faults into the spec only and assumes a correct record, so it cannot measure these. RFC-0028 already checks a record before its spec with a script, two unprimed readers and a primed review; a mechanical table check (G3) on the record is what it lacks.
    2. "Frozen, with no reopen left open" cannot be the freeze. BK-501's reopen answers each open item with a decision, but asks a ground conflict only its route: one routed to the ground artifact's own flow stays open until Flow done (axes.md § Per-question loop). OP-01/O21, TREE-001 against S3, may legitimately stay so, and RFC-0024 R1 forbids settling it on the side.
    3. Dafny to Python is not unavailable here. The research judged its literal Pipeline C unrunnable for want of a .NET toolchain; this repository compiles Dafny oracles to Python in Docker (scripts/dafny_translate.sh, BK-463) and plans an ITF replayer for TLA+ traces (BK-461), the bridge Pipeline C′ needs. Its warning stands: nine soundness bugs found by fuzzing in Dafny's back-ends, the Python one among them (deep dive § 2.3).
    4. OP-01 nearly meets the trial's criteria for its operation (trial design § 2.1, O1 to O11), on a first reading that the trial's own scoring replaces (Inference): case tables (D9, D34), a stream's state table (D18), an Environment with faults and with concurrent and out-of-band actors, an interval operation (D21, D22), a non-promise register (D41), profile deviations (D43), and documented real misreadings (the review's open items). It fails O8, a complete record frozen at a revision hash, until it is frozen (RFC-0029 R2), and O10 (not used in earlier trials or public reports) needs a judgement: the record is public on GitHub.
