    Research: The v1 operation catalogue against comparable libraries (BK-493)¶

    Date: 2026-10-26 Backlog items: BK-493 (The v1 Store API has no agreed set of operations, so each design session would find its own scope) Status: Research complete. Background to RFC-0026; it decides nothing. Not ground: its per-entry notes are for each entry's own session (RFC-0026 C4).

    Ten comparable libraries cut the catalogue's operations in different ways, and the most widely offered operation with no draft entry, a presigned URL, is in 8 of them. The cut stands, OP-20 and OP-09 widen, and every other operation found gets a disposition in the catalogue's Not in v1 list (§ 3). What the comparables most often had to retrofit is input to each entry's session, not to the catalogue.

    1. Question and method¶

    The maintainer tested the draft catalogue against what comparable libraries offer, from the brief in BK-493's dossier: completeness (Q1), the cut (Q2), which entries are gated and how a caller learns it (Q3), what is decided once for every operation (Q4), and pitfalls per entry (Q5). The full report, with a citation per claim, is reports/remote-store v1 operation catalogue verified.md in the haalfi/research repository at b0e426f. This document keeps its results and their consequences for the Store API.

    Comparables (10, the denominator for every "n/10"): fsspec, pyarrow.fs, Apache OpenDAL (Rust core and Python binding, counted as one), Rust object_store, Go gocloud.dev/blob, smart_open, cloudpathlib, and the AWS S3 (boto3), Azure Blob and Google Cloud Storage SDKs. Hadoop FileSystem, paramiko/SFTP and obstore are cited where needed but not counted. Versions are in § Sources; all were read on 2026-10-26.

    Evidence. Claims rest on documentation or released source unless marked. Inference marks the researcher's own reading. Observed marks a claim seen by running pyarrow, smart_open and cloudpathlib against local disk and the moto S3 emulator; observed on MinIO marks the user's run against a MinIO server of unstated version. Nothing was run against real AWS, Azure or GCS. Counts are lower bounds: an operation counts only where found in a full text.

    2. Results¶

    Q1. Completeness: operations no draft entry covered¶

    Operation Use case Count
    Presigned or signed URL Time-limited access without credentials 8/10
    System properties (content type, cache control) apart from user metadata HTTP serving 7/10
    Batch delete Many keys in few requests 6/10
    Versioned access History, recovery, pinned reads 6/10
    Integrity and identity tokens (checksums, unique keys, verified MD5) Verify transfers, detect change without reading 6/10
    Append Logs 6/10, always gated, sometimes emulated
    Conditional read Skip the transfer if unchanged 5/10
    Abort an in-flight write Drop a streamed or multipart upload 5/10
    Bucket or container create and delete Provisioning 5/10
    Server-side compose, restore or undelete Concatenation, recovery 4/10 each
    Multi-range read Columnar formats 3/10
    Delete only a folder's contents, or only an empty folder Guardrails 3/10
    Storage class, retention or legal hold Cost, compliance 3/10 each
    Post-write metadata update Fix a content type after upload 2/10 native (Azure, GCS); S3 rewrites the object
    Local cache layer, transparent compression, touch, tags, query in place Various 2/10 each
    Transaction, key-value view, FUSE mount, rsync, leases, snapshots, aborting an async copy, annotations Various 1/10 each

    Absent almost everywhere: OP-07's depth limit (fsspec only), OP-18's capability query (OpenDAL only) and OP-24's health check (OpenDAL and gocloud only; the vendor SDKs' calls in § 5's row 24 check that a bucket or container exists, and are not counted as health checks, inference).

    Q2. The cut¶

    • Write, atomic replace, conditional write (OP-03 to OP-05). The comparables merge them: a condition is a mode of put (object_store PutMode::{Overwrite, Create, Update}, every put atomic), and the vendor stores attach conditions to read, delete, copy, rename and metadata update as well. OpenDAL publishes a conditional-operations specification: a condition is never silently ignored, a mutation condition is advertised only if it is evaluated atomically with the visible commit (stat-then-mutate emulation is forbidden), staged writes evaluate it at the final commit, and where the error surfaces is unspecified. fsspec's mode="create" is exactly that forbidden emulation (inference). Atomic replace is a separate operation only on filesystems (os.replace, SFTP posix_rename); on object stores every PUT is atomic.
    • List, walk, match (OP-06 to OP-08). The least agreed cut. gocloud has one prefix-and-delimiter listing; object_store separates a recursive listing from a delimited one; pyarrow merges inspect, list and walk into one call; fsspec and cloudpathlib keep separate calls. Depth and pattern are emulated client-side at O(subtree) cost (inference); only GCS matches a glob server-side.
    • Inspect (OP-09). The comparables lean to one rich inspect call with derived probes; Hadoop deprecated single-attribute probes. The identity fields it returns are opaque tokens, not content hashes (Q4).
    • Delete (OP-10, OP-11). Tree delete is one call where it exists (fsspec, pyarrow, cloudpathlib, OpenDAL); object_store and gocloud have none.
    • Copy and transfer (OP-13 to OP-15). fsspec splits by locality; pyarrow's copy_files merges local and cross-store transfer; object_store copies within one store only.
    • Read (OP-01, OP-02). pyarrow splits sequential from random reads; object_store folds ranges into one get with options.

    Q3. Gating and how a caller learns it¶

    Strategy Who
    Declared and checked before dispatch OpenDAL: capability() with about 90 to 100 flags, a pre-dispatch check, and for conditions "never silently ignored"
    Configured per store, then an error at call time object_store, which also ignores unsupported tags but errors on unsupported attributes
    Error at call time only gocloud, pyarrow, cloudpathlib, smart_open
    Silent emulation or no-op fsspec mkdir does nothing and mv is copy plus delete; cloudpathlib mkdir does nothing; pyarrow drops metadata keys; smart_open ignores unknown parameters
    Path-scoped probe Hadoop hasPathCapability, where False may mean unknown

    OpenDAL gates create_dir, rename, copy, recursive listing, user metadata, append, presign and the conditional and versioned variants, which matches the catalogue's optional OP-19 and OP-20. Several gates depend on bucket or account type and are only found at runtime: Azure rename and recursive delete need a hierarchical namespace, S3 RenameObject needs Express One Zone. OpenDAL's flags are the effective set, simulations included, and were missed and fixed piecemeal.

    Q4. Decided once for every operation¶

    Decision What the comparables do
    Key validation object_store rejects or encodes ./.. and empty segments; OpenDAL passes .. through; gocloud escapes per driver; pyarrow, smart_open and cloudpathlib normalise none of .., . or // (observed). Vendor limits: S3 and GCS 1024 bytes, Azure 1024 characters and 254 segments
    Error taxonomy object_store Error enum and OpenDAL ErrorKind, each with NotFound, AlreadyExists, a precondition kind and an unsupported kind; gocloud ErrorCode; fsspec and pyarrow builtins
    Retries object_store built in, retrying a timeout only if the request is idempotent; OpenDAL opt-in, temporary errors only; s3fs an allow-list; gocloud not portable (inference); GCS retries deletes by default
    Timeouts per instance or per call: object_store 30 s, OpenDAL 60 s (opt-in), botocore 60 s, Azure 20 s to connect and 60 s to read, GCS 60 s; gocloud per call
    Consistency stated atomic put (object_store); strong read-after-write including list (S3, Azure, GCS); gocloud's list may miss recent writes
    Identity token ETag and version are opaque. An S3 ETag is an MD5 only for a single-part plaintext or SSE-S3 upload; multipart, SSE-C/KMS and directory buckets give no MD5, and a metadata-only change leaves the ETag alone
    Closing gocloud Bucket.Close; vendor close(); OpenDAL Operator, fsspec and pyarrow have none; object_store relies on Drop (inference)
    Async parity OpenDAL Python is not at parity (presign is async-only); fsspec and Azure offer both; boto3 and GCS are sync only
    Prefix scope (OP-16) object_store PrefixStore, OpenDAL root, gocloud PrefixedBucket, fsspec DirFileSystem, pyarrow SubTreeFileSystem

    .. containment was retrofitted in three libraries in 2026 (fsspec DirFileSystem, OpenDAL fs, cloudpathlib).

    Advisory notes (the report's, not decisions)¶

    1. Additions or explicit exclusions: presign (8/10), system properties next to OP-20 (7/10), batch delete, versioned access, integrity and identity tokens (6/10 each), append (6/10), conditional read and abort (5/10 each), multi-range read (3/10), delete guardrails (3/10), post-write metadata update (2/10 native).
    2. OP-05's scope. The vendor stores and OpenDAL attach conditions to more than writes; OpenDAL's specification defines them once: no silent drop, atomic with the commit, the error point unspecified, status codes alone not deciding the error kind.
    3. OP-07's depth limit has one precedent (fsspec) and costs O(subtree) on object stores.
    4. OP-09 and OP-14: ETag and version are opaque identity tokens; an S3 ETag cannot double as an integrity check.
    5. OP-18: OpenDAL's effective flags with a pre-dispatch check, Hadoop's "False means unknown", gates that depend on bucket type; object_store mixes silently ignoring one option with erroring on another.
    6. OP-24: a thin precedent (2/10), and the two disagree on whether a missing root is healthy.
    7. Shared decisions most often retrofitted: .. containment, missing-key delete, exception typing in Python bindings, sync and async parity in bindings, retry coupled to idempotency, behaviour on an exception during a streamed write.

    3. Consequences for the Store API¶

    What the catalogue and spec 053 took from the results (decision log sdd/decisions/c886d81c-7d81-58f9-bc3d-f11dc7304e4a.jsonl):

    Result Consequence
    Conditions attach to read, delete, copy and rename too (Q2, note 2) OP-05 stays a conditional write; conditions on other entries are not in v1
    List, walk and match is the least agreed cut; one precedent for a depth limit (Q2, note 3) OP-06 to OP-08 stay three entries; OP-07 keeps its depth limit
    System properties (7/10) and identity tokens (6/10) have no entry (Q1) OP-20 holds user metadata and system properties; OP-09's info holds an identity token where the backend offers one
    pyarrow and OpenDAL expose no native handle, boto3 no address mapping (§ 5, rows 22 and 23); an outside review on PR #1184 raised it OP-22 and OP-23 are optional
    Batch delete, abort, multi-range read, delete guardrails, post-write metadata update, checksum verification, touch, a key-value mapping view, rsync-style mirroring (Q1, § 5) Forms of OP-10, OP-03, OP-02, OP-11, OP-20, OP-03, OP-03, OP-17 and OP-15, for those entries' sessions
    Every other Q1 operation Not in v1; an extension may add one on top of the entries
    Gates are found at call time or silently ignored almost everywhere (Q3) One place answers what a store supports, OP-18, whose spec binds the catalogue's Offer column
    Shared decisions most often retrofitted (note 7) .. containment is spec 052's and async parity spec 053's; the rest is input to read()'s session and each later one (RFC-0026 Open Question 1)

    The Q1 table's dispositions are in the catalogue's Not in v1 list.

    4. Notes for each entry's session¶

    Pitfalls the comparables met, per entry, as input for that entry's session. A named file is admitted whole (§ 4, S3 of research-spec-first-reset.md), so handing a session only its own entry's notes waits on BK-494. None proposes semantics.

    • OP-01 Read. The view during a streamed read is undefined unless pinned; s3fs added ETag expiry checks. object_store returns NotFound on a folder path. pyarrow's allow_delayed_open defers open errors to close. cloudpathlib downloads the whole object first.
    • OP-02 Read at offsets. Ranges past the end were fixed separately in five libraries. Azure has no suffix range; S3 serves one range per request. Hadoop's vectored read may mix old and new data if the item changes. Observed on MinIO, not AWS: a range starting at or past the size gives 416, an end past the size is clamped, a suffix longer than the object returns all of it.
    • OP-03 Write. Visible only on close, and close can fail. On an exception, pyarrow commits the partial object, cloudpathlib uploads it and smart_open aborts (observed). Multipart has a 5 MiB part floor and at most 10,000 parts. Empty items take a separate path in several libraries. S3 adds a CRC64NVME checksum when none is supplied, and "AWS SDKs do not automatically calculate MD5 checksums".
    • OP-04 Replace atomically. Object-store PUT is atomic, but object_store's local temp files leak into the key space. Windows needs os.replace, SFTP posix_rename. A durable replace needs a directory fsync. On S3 the latest timestamp wins.
    • OP-05 Conditional write. Conflicts surface as 412, 409 or 404 (a concurrent delete). A delete marker counts as absent. A local filesystem cannot do "if unchanged" (object_store #423); "if absent" maps to O_EXCL. object_store separates AlreadyExists from a precondition failure. OpenDAL forbids stat-then-mutate emulation and evaluates staged writes at the final commit, leaving the old item on failure.
    • OP-06 List children. Directory markers changed policy across Hadoop releases. A missing folder is an error in Hadoop, optional in pyarrow and tolerated in OpenDAL. Ordering is not guaranteed in object_store, differs on S3 directory buckets and Azure HNS, and is lexicographic in gocloud. Pages can be short or empty; listing caches go stale.
    • OP-07 Walk subtree. Flat versus per-level listing is a real split; only per-level listing can prune. Cost is O(entries). gocloud's listing may miss recent writes.
    • OP-08 Match by pattern. fsspec's glob rules: ** must be a whole component, depth applies to the first **, a trailing / matches folders, no braces; they drifted across releases, as pathlib's did in 3.13. Metacharacters in keys need an escape. Only GCS matches server-side.
    • OP-09 Inspect. "Is it a folder" is ambiguous on object stores and costly to probe. An S3 HEAD on a missing key returns 403 without list permission. mtime is the multipart start time, at about 1 s granularity. The ETag is not a content hash (Q4); fsspec offers ukey and checksum as identity probes.
    • OP-10 Delete item. A missing key succeeds on S3 and in OpenDAL (even under a condition), and errors in object_store's local, GCP and Azure stores, gocloud, Azure and GCS; Hadoop returns False. Bulk limits are 1000, 256 and 100 keys per request, with partial failures. Versioned buckets insert delete markers. Observed on MinIO, not AWS: deleting a missing key gives 204, and a batch delete lists it as deleted.
    • OP-11 Delete folder tree. Not atomic and O(n), except on Azure HNS. pyarrow's S3 delete_dir("bucket") empties the bucket and then raises (observed). Markers must be deleted too; S3 directory buckets delete empty parents themselves.
    • OP-12 Move or rename. Copy plus delete is neither atomic nor cheap. Atomic only on some bucket types: Azure HNS, GCS move_blob within a bucket, S3 RenameObject on Express One Zone. SFTP v3 rename fails if the target exists. Same-path moves differ; GCS charges early deletion on a copy-based move.
    • OP-13 Copy within a store. S3 CopyObject is atomic up to 5 GB, and pyarrow uses only that call, so its S3 copy fails above it (the failure mode is inference). Azure copies can stay pending. Copying a multipart S3 object changes its checksum and so its ETag form.
    • OP-14 Transfer to or from a local file. Temp-file strategies differ (temp plus rename, direct write, cross-device rename). Comparing an ETag with a local MD5 fails for multipart, SSE-C/KMS and directory-bucket objects; gocloud verifies ContentMD5 on close. cloudpathlib fixed a .. escape (GHSA-r4f8-3xc4-c8vw).
    • OP-15 Transfer between stores. Data passes through the client and often local disk. fsspec's copy ignores errors by default. Two buckets of one provider are a third case. ETags are not comparable across stores or upload methods.
    • OP-16 Scope to a folder. .. escapes were fixed in 2026 in three libraries; pyarrow's SubTreeFileSystem "makes no security guarantee", and object_store's local store follows symlinks out of the root. Every method must be forwarded. gocloud's PrefixedBucket closes its parent.
    • OP-17 Hand items to other libraries. Bridges drop data (metadata, attributes, modes) and break when the wrapped library changes. gocloud's Bucket implements Go's io/fs.FS; cloudpathlib's fspath is a read-only cache copy.
    • OP-18 Ask what a store supports. Only OpenDAL and Hadoop have a query. Separate flags do not imply support for their combination; capabilities depend on path or bucket type; flags were missed and fixed piecemeal.
    • OP-19 Create an empty folder. One intent, different results: a zero-byte key/ marker (pyarrow), a silent no-op (cloudpathlib), a new bucket (s3fs, gcsfs), a real folder (GCS HNS). None in object_store or gocloud.
    • OP-20 Item metadata. Limits differ: S3 2 KB, lowercase US-ASCII keys, changed only by copy; Azure 8 KB, identifier keys, a set replaced whole; GCS 8 KiB, patchable. pyarrow's S3 drops user keys silently (observed). object_store mixes system and user metadata and ignores tags where unsupported.
    • OP-21 Close a store. Most comparables have no close. fsspec caches instances by their arguments; async close at garbage collection is fragile; a derived handle takes over the lifecycle.
    • OP-22 Map a key to its native address. Many URL forms map to one store, and the logical key is not always the native key (percent-encoding, escaping). pyarrow embeds credentials in URIs; smart_open accepts them.
    • OP-23 Reach the native client. gocloud's As "implies that the resulting code is no longer portable". The handle may be uninitialised or bound to an event loop (s3fs).
    • OP-24 Check health. OpenDAL's check() treats a missing root as healthy, gocloud's IsAccessible as not. "Healthy" usually means list permission; S3 HeadBucket answers 400, 403 or 404 with no body.

    6. Limits¶

    • Nothing was run against real AWS, Azure or GCS. The MinIO observations under OP-02 and OP-10 match RFC 9110 and the AWS documentation but do not verify AWS itself.
    • OpenDAL's conditional-operations specification is a moving page ("Last updated on Aug 31, 2026"), not pinned to a release. The pre-1.0 crates (object_store, OpenDAL) and the S3 conditional-operation matrix change often.
    • Some fsspec, OpenDAL and object_store source was read on main, possibly slightly ahead of the release in § Sources; smart_open's docs come from its development branch.
    • Unverified: the content of fsspec 2023.9.0's glob change, and reports that botocore 1.36 broke S3-compatible servers.
