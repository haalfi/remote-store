Where the tokens went

Almost all spend is the model re-reading its own context on every call. 98.7% of tokens are cache reads, worth 80% of the dollars. A session costs roughly calls × context size, so four long sessions took 84% of the spend. In the /ship and release sessions, more than half of the cost came after the PR opened.

Sample size. The 8-week window holds only two working days: 2026-09-05 (Opus 5) and 2026-10-04 (Opus 5.5). Cloud sessions and the analysis session itself are not included. The 2026-09-05 transcripts were deleted by Claude Code's ~30-day cleanup while this analysis ran. The figures come from an extract taken before the deletion and can no longer be re-derived from disk. Read everything here as a description of two days, not as statistics.

Cost grows faster than session length

Each call costs about 0.1 × its context. Context grows 1.4k to 2.0k tokens per call in the long sessions. Across main sessions, cost grows faster than length: a session with twice the calls costs about 2.3 times as much (a log-log fit gives an exponent of 1.19). Subagents stay short, so their exponent is 0.91, close to linear. In the four largest sessions, half the units are spent after 59 to 67% of the calls.

What the long review loops are made of

Code and test findings settle within a round or two of the last code fix; the long tail is prose. The data says why: the prose is dense with checkable claims that nothing checks except the next review round, and each round's fixes make other claims false.

  • Prose leads from round 1. Of 650 top-level review comments on 41 PRs, 399 are on prose files, 59 on traces and 186 on code or tests. Prose and traces are 68% of round 1 and 84% from round 9 on.
  • Two kinds of long loop. Decision PRs (#1045 ADR-0042, #1061 key rule, #1066 RFC-0019, #1056) ran 10–13 rounds with no code findings at all. Gate and tooling PRs whose code is defined in prose (#1027, #1047, #1048, #1052, #1053) ran 8–20 rounds with code findings to the end.
  • Pure code converges fast. Of the 24 PRs with a code or test finding, the median has no round with findings after the last one, and 4 have two or more. The other 17 drew prose and trace findings only.

Context the run never gathered

The maintainer stopped the BUG-280 run after round 7 with one question: would the backend redesign (BK-389, BK-394) make this simpler and better? The session halted and narrowed the open PR heavily. BK-389 and RFC-0017 were in context from the run's second call; the run recorded no verdict on the related items before planning.

  • The orient phase was tiny. 9 calls, 0.7% of the run's units, and none of them looked for related open work.
  • BK-389 appeared only by accident. It surfaced at call 2 inside a BACKLOG.md read, as a mention in a neighbouring item (BUG-245), not in relation to BUG-280. BK-394 and ADR-0042 first appear at call 414, right after the maintainer's question.
  • The link was already in the backlog. BUG-280 lists spec BE-021; so do BK-389 and BK-394. A query for open items sharing a spec ID would have surfaced both redesign items before any code was written.
  • What skipping it cost. The review loop and its subagents took about 28 M units (89% of the run) hardening an error model that the redesign would reshape. Not all of it is lost: the permission-leak fix itself stays. But most of seven rounds went into making a stopgap watertight.

The cost figure is the run's post-PR share at the round-7 checkpoint; how much of it survives the narrowing is not yet measured.

Summary and hypotheses to act on

Cost is set by how many calls a session makes and how large its context has grown by then. Every content type is multiplied by the calls that follow it, so the same item costs more the earlier it enters and the longer the session runs. Each hypothesis below names its evidence, the largest share of spend it could move, and the measurement that would confirm or refute it.

Ceilings are the share of re-read context or units the factor accounts for in this sample. They can overlap and don't add up. They bound what acting on a hypothesis could move; they don't predict a saving. With two working days and one dominant session, each hypothesis needs its test on new data before anyone acts on it.

Method. All Claude Code transcripts of this repository and its worktrees whose first record falls in the window were parsed into one row per API call (usage, model, skill, TTL split) and one row per content item (tool result, attachment, tool input). Calls were deduplicated by message id. An item's carried cost is its calibrated size times the calls it stays in context, until a compaction. Hidden thinking is estimated as output tokens minus visible output.
Limits. Two working days. One Opus 5 session dominates, and Opus 5 cost about 2.2× Opus 5.5 per token. Prices are fitted, not list prices. report_token_usage.py assumes 4 characters per token and leaves out the prefix and thinking, so its "carried" ranking misses about a third of context and undercounts tool results by about 1.7×.
