# ADR-0032: Tiered per-PR CI gate with a full-matrix backstop

## Status

| Field         | Value    |
| ------------- | -------- |
| Status        | Accepted |
| Supersedes    | —        |
| Superseded by | —        |

Builds on the Stage model of
[ADR-0028](0028-testing-architecture-kind-stage-replay.md) (Stage 1 = repo-only,
Stage 2 = live Docker backends). The stage model itself is unchanged; this ADR
decides only how the stages are distributed across CI jobs. See spec
[048 § TEST-006](../specs/048-testing-architecture.md) for the CI mapping this
records, and `sdd/CI-OPERATIONS.md` for the operational runbook.

## Context

The per-PR `ci.yml` gate took ~8–9 minutes. Its shape ran the full two-pass
live-backend suite — pass-1 `pytest -n auto` (~326 s) then serial `sftp_docker`
(~100 s) — on **all five** supported interpreters (3.10–3.14) in parallel, so the
slowest interpreter set the wall-clock. The goal (BK-319) was a sub-5-minute
PR-to-green gate with every existing guarantee preserved: full support-matrix
correctness, real-backend fidelity, the 95 % coverage floor, cross-platform,
docs/examples/notebooks/package, and formal-spec parity.

The constraints and the levers that do **not** work were established by
measurement on real runners:

- **20 concurrent jobs.** The repository is under a personal GitHub account, so
  it is capped at 20 concurrent jobs; **merge queue** and **larger runners** are
  organization-only and unavailable. Every guarantee must therefore fit inside 20
  lanes on standard 4-vCPU runners — work cannot be moved to a merge queue or
  bigger hardware. (This cap is an account-plan attribute that changes with no
  repo diff; it lives here as the single citable source — living prose elsewhere
  should reference BK-319 / this ADR rather than restate the number.)
- **xdist oversubscription does not help.** `-n 8` / `-n 12` were no faster than
  `-n auto` — the suite is CPU-bound, not I/O-bound, so more workers per runner
  buys nothing.
- **Sharding the live-backend suite is inefficient.** Each shard re-pays the
  per-test live-backend fixture setup (bucket creation, container handshakes), so
  a 2-way split of the 3.10 leg summed to ~460 s of wall — worse than the 326 s
  single job.
- **Call-time durations mis-balance shards.** `pytest-split --store-durations`
  records only call-phase time, but live-backend and `azure_replay` (VCR) work
  happens in *setup*; a naive split ran one shard ~1.8× the other.

## Decision

The per-PR gate is split by **test tier**, and the full per-interpreter live
guarantee moves to a scheduled/on-master backstop:

- **Primary interpreter (3.13) — full fidelity per PR.** `test-primary` runs the
  full live-backend Stage-2 pass-1, `pytest-split`-sharded with the
  `least_duration` algorithm over a **setup-inclusive** `.test_durations_pass1`
  (generated by `scripts/gen_split_durations.py`); `test-primary-sftp` runs the
  serial `sftp_docker` conformance; `coverage-gate` combines the shard partials
  (`parallel=true` + `relative_files=true`) and asserts the **unchanged 95 %
  floor**. The two interpreter-independent `TestCommittedCassettePIISweep`
  hygiene scans run once in `test-cassette-pii`.
- **Non-primary interpreters (3.10/3.11/3.12/3.14) — Stage 1 per PR.** The `test`
  matrix runs the repo-only Stage-1 tier (no Docker), sharded, exercising every
  Store/adapter code path so interpreter-specific breakage still blocks the PR.
- **`ci-full.yml` — full-matrix backstop.** The complete two-pass live-backend
  suite on **every** interpreter runs nightly and on every push to master,
  restoring the pre-BK-319 guarantee off the per-PR critical path.

**The guarantee tradeoff (owner-approved):** a regression that manifests *only*
on a non-primary interpreter *against a live backend* is caught by `ci-full`
(within minutes of merge, or overnight) instead of blocking that individual PR.
Every other guarantee still gates each PR. Result: PR wall-clock ~4m15s (measured
257 s), coverage 98 %.

*Reverse if* the tradeoff bites in practice — i.e. a non-primary-interpreter,
live-backend-only regression actually slips past the per-PR gate and reaches a
release — or the account gains merge-queue/larger-runner capacity (e.g. moves to
an organization), at which point the full matrix can return to the per-PR gate
directly.

## Consequences

- **Positive:** PR-to-green drops from ~8–9 min to ~4m15s; no guarantee is
  permanently dropped — the full live matrix still runs, just off the per-PR
  path; the primary interpreter keeps full live fidelity + the 95 % floor every
  PR.
- **Negative / neutral:** non-primary live-backend regressions surface post-merge
  rather than blocking the PR (the tradeoff above). A release manager confirming
  "CI green on master" must now also confirm the `ci-full.yml` run — the release
  checklist and `sdd/CI-OPERATIONS.md` reference it explicitly.
- **Maintenance surface:** two new artifacts carry ongoing duty — the committed
  `.test_durations_pass1` needs periodic refresh (stale durations degrade shard
  balance silently; the refresh flow is `scripts/gen_split_durations.py`, gated
  because `.test_durations_pass1` is in `CODE_PAT`), and the `ci-full.yml`
  interpreter matrix duplicates `ci.yml`'s `ALL_PYTHONS` (now pinned equal by
  `scripts/check_ci_full_matrix.py` in the lint gate).
