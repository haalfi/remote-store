## Pitfalls comparables met

Item metadata: Limits differ: S3 2 KB, lowercase US-ASCII keys, changed only by copy; Azure 8 KB, identifier keys, a set replaced whole; GCS 8 KiB, patchable. pyarrow's S3 drops user keys silently (observed). object_store mixes system and user metadata and ignores tags where unsupported.

## Findings in the research's results

§ 1, the denominator: **Comparables (10, the denominator for every "n/10"):**
fsspec, pyarrow.fs, Apache OpenDAL (Rust core and Python binding, counted as
one), Rust `object_store`, Go `gocloud.dev/blob`, smart_open, cloudpathlib, and
the AWS S3 (boto3), Azure Blob and Google Cloud Storage SDKs. Hadoop FileSystem,
paramiko/SFTP and obstore are cited where needed but not counted. Counts are
lower bounds: an operation counts only where found in a full text.

Q1, an operation no draft entry covered: System properties (content type, cache
control) apart from user metadata; HTTP serving; 7/10.

Q1, an operation no draft entry covered: Post-write metadata update; Fix a
content type after upload; 2/10 native (Azure, GCS); S3 rewrites the object.

Q3, gating: OpenDAL gates create_dir, rename, copy, recursive listing, user
metadata, append, presign and the conditional and versioned variants, which
matches the catalogue's optional OP-19 and OP-20.

Q3, gating: Configured per store, then an error at call time: object_store,
which also ignores unsupported tags but errors on unsupported attributes.

Q3, gating: Silent emulation or no-op: fsspec `mkdir` does nothing and `mv` is
copy plus delete; cloudpathlib `mkdir` does nothing; pyarrow drops metadata
keys; smart_open ignores unknown parameters.
