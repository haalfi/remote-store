## Pitfalls comparables met

Copy within a store: S3 `CopyObject` is atomic up to 5 GB, and pyarrow uses only that call, so its S3 copy fails above it (the failure mode is inference). Azure copies can stay pending. Copying a multipart S3 object changes its checksum and so its ETag form.

## Findings in the research's results

Q2, the cut, write, atomic replace, conditional write (OP-03 to OP-05): The
comparables merge them: a condition is a mode of put (object_store
`PutMode::{Overwrite, Create, Update}`, every put atomic), and the vendor stores
attach conditions to read, delete, copy, rename and metadata update as well.
OpenDAL publishes a conditional-operations specification: a condition is never
silently ignored, a mutation condition is advertised only if it is evaluated
atomically with the visible commit (stat-then-mutate emulation is forbidden),
staged writes evaluate it at the final commit, and where the error surfaces is
unspecified. fsspec's `mode="create"` is exactly that forbidden emulation
(inference). Atomic replace is a separate operation only on filesystems
(`os.replace`, SFTP `posix_rename`); on object stores every PUT is atomic.

Q2, the cut, copy and transfer (OP-13 to OP-15): fsspec splits by locality;
pyarrow's `copy_files` merges local and cross-store transfer; object_store
copies within one store only.

Q3, gating: Silent emulation or no-op: fsspec `mkdir` does nothing and `mv` is
copy plus delete; cloudpathlib `mkdir` does nothing; pyarrow drops metadata
keys; smart_open ignores unknown parameters.

Q3, gating: OpenDAL gates create_dir, rename, copy, recursive listing, user
metadata, append, presign and the conditional and versioned variants, which
matches the catalogue's optional OP-19 and OP-20.
